# Design

## Context

- The only table is `events`. It was created by hand from `server/sql/schema.sql` on the Neon
  `production` branch (production) and the `dev` branch (local runs). It has rows that must stay.
- `server/src/analytics.ts` writes with a tagged `neon()` query built on each insert, so a
  missing `DATABASE_URL` only fails that write and is logged. The app must keep working without
  a database.
- `server/src/app.test.ts` mocks `@neondatabase/serverless` and checks the inserted values in
  column order.
- Deploys use Cloud Run continuous deployment: a Cloud Build trigger, generated by Cloud Run,
  builds the root `Dockerfile` and deploys it. The image keeps production dependencies only.
- CI (`.github/workflows/ci.yml`) runs lint and tests on every push and pull request, with no
  database.

## Goals / Non-Goals

**Goals:**

- One migration runner used locally, in CI and in the deploy.
- Tests stay offline and fast.

**Non-Goals:**

- No new tables or columns; `events` stays exactly as it is.
- No seed data, no Drizzle Studio, no relational query setup.
- Local `pnpm dev` keeps writing analytics to the Neon `dev` branch when `DATABASE_URL` is set,
  as today; PGlite is for tests only.

## Decisions

**Drizzle stable, not the 1.0 beta.** Use the current `latest` tags (`drizzle-orm` 0.45,
`drizzle-kit` 0.31). The 1.0 line is still beta and changes the migration folder layout.

**Files.** `server/drizzle.config.ts` (dialect `postgresql`, schema `src/db/schema.ts`, out
`drizzle`). `server/src/db/schema.ts` holds the `events` table. `server/src/db/client.ts`
exports the Neon HTTP Drizzle client. `server/src/db/migrate.ts` applies migrations.
Migrations live in `server/drizzle/`, which the Docker build already copies.

**Schema matches the live table exactly.** `id` is `bigint` generated always as identity,
primary key; `at` is `timestamptz` not null default `now()`; `kind` and `visitor` are not null
`text`; `country`, `framework` are `text`; `status` is `smallint`; `prompt_tokens`,
`completion_tokens` are `integer`; `cost` is `numeric`. The check is named `events_kind_check`,
the name Postgres gave the inline check, so the two schemas compare equal.

**Baseline with `CREATE TABLE IF NOT EXISTS`.** The generated first migration is edited once,
before it is ever applied, to add `IF NOT EXISTS`. On production and `dev` it is a no-op that
gets recorded as applied; on an empty database it creates the table. Alternative rejected:
inserting the migration's hash into `drizzle.__drizzle_migrations` on production by hand, which
is a hand change on production and easy to get wrong. Later migrations are never edited.

**Migrations run through `drizzle-orm`'s migrator, not `drizzle-kit migrate`.**
`src/db/migrate.ts` calls `migrate()` from `drizzle-orm/neon-serverless/migrator` (a `Pool`
over WebSockets, built into Node 22) with the folder resolved from the file's own location, so it
works from `src/` (tsx) and `dist/` (node). It applies all pending migrations in one transaction,
so a failure leaves the database as it was. The `neon-http` migrator was rejected during
implementation: its docs say it has no transactions and does not roll back a failed migration.
`db:migrate` runs it with tsx and the repo `.env`; the deploy runs the compiled
`server/dist/db/migrate.js` inside the built image. `drizzle-kit` stays a dev dependency used
only by `db:generate`. Alternative rejected: `drizzle-kit migrate` in the deploy, which needs
dev dependencies in the image or a second install in Cloud Build.

**Tests use PGlite (chosen by the user).** In-process Postgres: no Docker (Windows Home), no
network, a fresh database per test file. `app.test.ts` mocks `./db/client.js` to return a
Drizzle PGlite client with the migrations applied by `drizzle-orm/pglite/migrator`, and the
analytics tests read rows back from `events` instead of checking captured values. This also
proves that the migrations build the table on an empty database. Alternatives: a Neon branch per
developer (closest to production, but network and a branch per run); Postgres in Docker (needs
Docker Desktop and WSL2). The driver differs from production, which the CI Neon job covers.

**CI Neon job.** A new `db` job in `ci.yml`, on pull requests only: create a branch
`pr-<number>` from `production` with `neondatabase/create-branch-action`, run `pnpm --filter server
db:migrate` and `pnpm --filter server test` with its `DATABASE_URL`, then delete it with
`neondatabase/delete-branch-action` under `if: always()`. Branching from `production` tests each
migration on a copy of production data, including the `IF NOT EXISTS` baseline. A
`src/db/client.test.ts` runs only when `DATABASE_URL` is set: it inserts an event through the
real Neon client and reads it back, so the production driver is tested on the branch. Secrets:
`NEON_API_KEY` (secret) and `NEON_PROJECT_ID` (variable). Action versions are checked against
current docs when written.

**Deploy with `cloudbuild.yaml`.** Steps: build the image, push it, run
`node server/dist/db/migrate.js` in that image with `DATABASE_URL` from Secret Manager
(`availableSecrets`), then `gcloud run deploy` with the same image. Steps run in order and a
failing step ends the build, so a failed migration means no deploy. It keeps the substitutions
the generated trigger already passes (`_SERVICE_NAME`, `_DEPLOY_REGION`, `_AR_HOSTNAME`, and so
on). Switching the trigger to this file is a console step for the user, recorded in
`docs/hosting.md`. No access grant is needed: the trigger runs as the default compute service
account, which already reads the `DATABASE_URL` secret for the Cloud Run service.

**Analytics through Drizzle.** `insert()` becomes `db().insert(events).values({...})`, where
`db()` builds the Neon Drizzle client on each call, keeping today's behavior that a missing
`DATABASE_URL` fails only that write. The fields written do not change.

## Risks / Trade-offs

- [Generated SQL differs from the live table (for example identity or check options)] → compare
  the migrated fresh database with production before merging (Neon schema compare), and fix the
  Drizzle schema, not the live table.
- [The `IF NOT EXISTS` edit hides a real difference on production] → the same comparison; the
  edit only skips creation, so any column difference shows up there.
- [PGlite behaves differently from Neon] → the CI job runs the real driver and migrations on a
  Neon branch.
- [A Neon branch is left behind and the free plan runs out of branches] → delete step under
  `if: always()`; branches named `pr-<number>`, so a leftover is visible and reused by the next
  run of the same pull request.
- [Pull requests from forks have no secrets] → acceptable for a solo project; the `db` job fails
  visibly rather than skipping.
- [Migration runs while the old revision serves] → migrations stay backward compatible (add
  first, remove later), as the spec requires.

## Migration Plan

1. Merge with the trigger still on the generated build: nothing reads the migrations yet, and the
   app writes the same rows.
2. Run `pnpm db:migrate` against `dev`, then let the switched trigger run it on `production`; both are
   no-ops recorded as applied.
3. Check: a fresh database built from migrations matches `production`; "Smoke live" passes; a visit on
   the live URL adds a row to `events`.

Rollback: switch the trigger back to the generated build. The `drizzle` schema with its
migrations table can stay; it does not affect `events`.
